# Simulator-Lab 开发路线图

更新：2026-11-04。**M1 已在固定原版 Ironclad/A0 和声明内容范围通过最终验收。** [最终报告](M1_FINAL_ACCEPTANCE.md)记录自然完整胜利、真实死亡、六样本/重放、可信数据和已知边界。先发布已验收 M1；本轮没有启动性能/策略新实验或 M2 公开 Mod 接口。下文保留路线及设计时的历史基础。

## 1. 主线与两个大里程碑

目标是建设一个使用合法本机游戏程序集、无需游戏界面的离线实验室：能够实际执行对局，取得可信数据，再为外部 Mod 提供经过验证的扩展接口。离线不要求另写一套脱离游戏程序集的完整规则引擎。

| 正式里程碑 | 核心交付 | 完成门槛 |
| --- | --- | --- |
| **M1-NativeRun：原版原生离线完整流程与可信数据** | 固定游戏版本、原版首个角色，从新 run 经真实节点、选择和幕转换，执行到终局；事件与状态数据可核查、可重放 | 有实际完整 RunVictory 路径、实际 Death 路径、规定房间类别与数据契约证据；预登记批次的执行可靠性通过。早死、首幕胜利或两战成功均不能单独关闭 M1 |
| **M2-PublicMod：公开 Mod 接口与 Eleanor 验收** | 根据 M1 已稳定的实际需求整理公开接口、版本与能力协议、文档及一致性检查；Eleanor 通过这些接口接入 | Eleanor 在声明的完整流程与数据范围通过真实验收，运行驱动没有隐藏的 Eleanor 特判；不要求所有 Mod 自动兼容 |

预测能力、战斗决策、奖励与路线策略贯穿两阶段，但分别设指标。**原生执行能力与 fork 预测能力分别声明**：原生能执行的内容不必先有镜像；没有预测支持时应记录 `NotCompared`，而非伪造差分通过。策略必须合法且可解释，不要求必胜、最优或穷举所有分支。

新里程碑的详细方案见 [MILESTONE_1_NATIVE_RUN_PLAN.md](MILESTONE_1_NATIVE_RUN_PLAN.md)。该文中的 N0–N6 是 M1 工作包，不是旧阶段编号。

## 3. M1 的产品边界与路线

建议首条路径为 **原版 Ironclad、单人 Standard、Ascension 0、固定声明的已解锁实验档案、默认 Acts**。不加载 Eleanor、BaseLib 或 Ritsu 的 Mod 功能；必要宿主库单独锁定。不开真实游戏界面，不读取或写入用户进度。完整 run 指该配置从正常开局到最终原生 RunVictory，不以击败某场 Boss 代替；Death 是有效策略结果，但仍须另有完整胜利路径证据。

内容按依赖推进：

1. **N0：冻结输入与安全宿主，确定结果和数据契约。** 识别 TestMode 语义分叉、原生选择入口与所有终局保存入口。
2. **N1：小型纵向判别。** 不依赖 CombatSolver，完成自然开局、战斗、原生奖励与下一合法节点；并用明确标注的后期夹具提前探测幕转换和最终事件的宿主风险。
3. **N2：选择与数据可信门。** Bundle 非首项选择、嵌套／隐式选择、实例身份、异步故障传播、清理前历史采集及观察不扰动。
4. **N3：节点类别与第一幕。** 休息升级、事件、商店、宝箱、遗物、药水、精英和 Boss 的实际协议；先各自有边界证据，再同一 run 组合。
5. **N4–N5：真实幕转换与完整 run。** 跨幕持久状态和原生最终 Architect／RunVictory；实际 Death 与独立进程退出。
6. **N6：同构建批测、数据查询与独立验收。** 预登记种子、保留失败分母、重放与采集开销分析，交付可复现的离线执行入口。

上述每一步的交付物、前置条件与失败门见实施方案。计划没有未经测量的工期承诺。后期夹具用于提前揭示依赖，不能充当从开局自然获胜的证据。

### 不纳入 M1 的目标

- 全角色、全难度、全种子、全部事件分支和遗物组合。
- 多人、Daily、解锁进度积累、真实存档恢复、Steam/云端功能与零售界面验收。
- 每张原版牌都可 fork、全 run 状态复制、全局最优策略或可靠整局胜率结论。
- 新增 Eleanor 卡牌／玩法、继续扩大 Mod 专项矩阵、公开 SDK 或替外部 Mod 承诺兼容。

已声明范围内的未知行为必须明确停止或归为 `Unsupported`。不能为了保持推进而跳过实际效果、伪造奖励、调整 HP、重置 RNG 或把测试替代路径冒充自然流程。

## 4. 架构方向

采用“**原生执行主干 + 可替换策略 + 独立采集 + 可选预测**”。

- **原生 host** 负责固定程序集、主线程 pump、内存保存、无 UI 依赖与安全边界。原生模型和命令执行效果，Lab 不逐牌重写原生规则。
- **run 生命周期控制器** 负责当前房间、待完成任务、合法决策时点、奖励、行进、幕与终局；不能只循环调用当前两战函数。
- **内部动作与选择协议** 传递来源状态、实例、候选、数量与实际选择，单次消费并拒绝旧票据；先满足原版已出现的需求，不设计公开 SDK。
- **策略端口** 默认提供合法简单策略；CombatSolver 是可选战斗策略。覆盖脚本、冻结重放、在线求解分别标记。未知预测能力可以显式退回原生策略，未知原生语义不能被略过。
- **观察与结果协议** 独立于 solver snapshot；RunVictory、BattleVictory、Death、预算／执行／数据失败分开，原生结果不得自动填入模拟结果。
- **预测端口** 保留已有审计、root／fork、完整 continuation 比较；支持多少就声明多少。不得通过放宽旧比较规则接纳原生独立执行。

M1 涉及有边界的驱动重构，主要拆开 Eleanor、solver 和两战脚本的耦合。先在现有构建与 harness 内形成清楚职责，是否拆独立项目由依赖证据决定。既不推倒已有保障，也不要求先造通用框架。

## 5. 四组指标与证据规则

| 维度 | 指标与门槛 | 不可混淆 |
| --- | --- | --- |
| 语义与隔离正确性 | 原生合法命令、独立契约、源状态不被观察／查询改变；已支持预测继续严格差分 | 双方一致不等于双方正确；无预测不等于原生失败 |
| 执行与数据覆盖 | 实际经过的节点／机制、到达终局、缺数据、unsupported 与非完成原因 | 早死不能证明后期支持；成功样本不能取代失败样本 |
| 策略质量 | 在相同信息权限、声明预算和预登记条件下比较 HP、资源和终局 | 同 seed 的不同策略可能改变 RNG 消耗；重复不是独立样本 |
| 性能 | 初始化、原生执行、采集、求解、序列化的耗时／内存／日志大小分别测量 | 不靠关闭校验换吞吐；有限预算不代表最优 |

原始观察与汇总分开，汇总须能由原始记录重算。玩家可见数据与 oracle 内部状态分开，不能把隐藏抽牌顺序、RNG 或完整状态 hash 暴露给声称只看可见信息的策略。错误、预算耗尽、取消、unsupported、策略死亡与完整胜利均保留。

## 6. 暂停、保留与迁移

| 处理 | 范围 |
| --- | --- |
| 暂停新增 | Mod 专项镜像扩展、未知 Eleanor 监听器适配、六张候选 Echo 卡、公开接口设计与全角色平衡实验 |
| 保留回归 | 已冻结 Eleanor、两卡修复、旧 Stage 1、原版战斗／RNG／奖励证据及其明确限制 |
| 迁移复用 | 安全 host、版本锁、选择与实例身份、拒绝非法字段、动作前缀、失败传播、实际终态、回放、独立契约 |
| 新主线必要修复 | 通用原生动作、房间同步、数据采集、生命周期与保存隔离；这些共享问题的修复不构成重新启动 Mod 专项 |
| 延后优化 | 全局规划、复杂评估函数、并行 fork、大规模性能调优；仅在测量显示其阻碍 M1 时处理窄问题 |

共享改动应跑已有冻结 Mod 的适用回归；发现回归须诊断是否损伤共享契约。不能删除旧检查使主线变绿，也不能借机扩张角色支持范围。

## 7. M1 完工与 M2 入口

关闭 M1 必须同时满足：

- 固定配置、合法本机输入、无 UI 原生执行入口可重现，保存／网络边界有证据。
- 从正常开局实际经过所有默认 Acts 到原生 RunVictory 的完整轨迹及同输入冻结重放；另有真实 Death，不能把胜利后的原生清场减血判成死亡。
- 规定房间类别和非首项选择有证据；未覆盖组合列清单，不能宣称全内容。
- 跨节点／幕持久状态和战斗临时状态按原生规则处理，保存清理前后观测。
- 最小数据契约、来源／实例／顺序关联、完整性检查、故障传播及观察不扰动通过。
- 预登记批次、真实退出状态、终局／停止分类、最后确认边界、重放与同构建回归可审查。
- 独立验收确认没有用夹具、solver 预测、空历史或外层 exit 0 代替实际执行证据。

进入 M2 前再冻结第一版公共契约草案：内容发现与来源、初始化与清理、选择、状态／实例、数据观察、错误／能力和版本协议。**原生扩展、观察扩展、可选 fork 适配是不同能力**，不要求每个 Mod 都提供预测镜像才能原生运行。只有被真实原版流程验证过的内部边界才晋升为公共承诺。

M2 的 Eleanor 验收须使用固定真实程序集／manifest，通过公开接口完成声明的代表性完整流程与机制矩阵；如果仍需改核心驱动或绕过审计，记录为接口缺口。公共文档、最小示例、许可边界与兼容测试齐备后再讨论发布，不在本轮发布。

## 8. 执行与协作规则

- 关键架构与关口由 Astra xhigh 审查，Sol xhigh 分工作包实现；沿用 Standard。模型安排是后续执行建议，不代表本轮启动了多个代理或变更会话配置。
- 一名集成负责人拥有 host／生命周期和结果协议；数据与独立检查可在冻结契约后并行，房间适配按独立文件负责。共享构建缓存与最终集成回归串行运行。
- 每个自然检查点报告实际完成、运行中、未运行与阻塞；未知结果先核查，不能重复派发状态不确定的动作。
- 所有新证据绑定真实 dirty 源码、构建配方、工具链、产物及输入哈希；旧结果保留，不能用新源码解释旧产物。
- 仓库只保留项目代码、必要工具与可公开文档；游戏程序集、反编译内容、用户路径、研究资料、凭据、Agent 文件和原始运行产物留在本地。保留 MIT 与第三方归属，不把依赖当作 Lab 许可发布。
- 未有新授权前不提交／推送，不改角色工程或游戏安装，不读写真实存档，不启动游戏 UI。实施进度只以对应验证文档的真实范围为准。
