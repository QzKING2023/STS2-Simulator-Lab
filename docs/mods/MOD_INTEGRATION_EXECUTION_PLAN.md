# Mod 接入与兼容性阶段计划

## 目的

Simulator Lab 已经完成原版回放。下一阶段建立面向已编译 Mod 的公开适配边界，先让一个简单角色形成可重复的端到端闭环，再按内容表面逐步扩大覆盖范围。

适配目标是黑盒接入。Workshop 包作为外部输入，核心模拟器只依赖内部标准模型和受审计的运行时桥接，不把任意 Mod 类型、静态字段或 Godot 对象直接泄漏到核心逻辑。

固定版本规则如下。

- Workshop ID 只作为来源身份，不能单独当作版本号。
- 快照目录和清单文件名带捕获时间，内容摘要由排序后的路径、大小和 SHA-256 计算。
- 任一文件内容或长度变化都必须生成新的快照目录和新的摘要，禁止覆盖旧快照。
- 运行目标先固定为游戏 `0.111.0`。存在兼容变体时只选择精确匹配，禁止静默回退到其他游戏版本。
- 运行器只读快照。任何需要写入的设置、存档或临时产物都必须导向新建的 `.build` 工作目录。

## 目标适配边界

### 输入层

- `ModSource` 记录快照 ID、Workshop ID、相对路径、来源摘要和捕获时间。
- `ModManifest` 记录 Mod ID、显示名、版本、最低游戏版本、玩法标志、依赖和包文件清单。
- `ModCatalog` 对快照内所有条目做稳定排序，拒绝重复 Mod ID 和重复来源。
- `DependencyResolver` 针对游戏 `0.111.0` 解析精确兼容变体，输出加载顺序和缺失依赖。

### 黑盒运行层

- 先读取 manifest 和 PE 元数据，再进入运行时探针。静态发现不能冒充玩法支持。
- Mod DLL 不加载进核心模拟器进程。使用独立 worker 进程和受限的只读 ModManager 文件视图。
- 禁止访问真实 Workshop 枚举、玩家存档、正式设置和正式游戏数据。任何写入尝试都记录为隔离失败。
- 原始 DLL、PCK 和资源不反编译、不改写、不合并。适配代码只消费公开 manifest、受控探针结果和标准化运行时事件。
- 每次探针使用新进程，避免静态注册表、Harmony 补丁和 Godot 全局状态污染后续案例。

### 内部标准模型

核心模拟器只依赖以下稳定模型。

- `ModPackage` 和 `ModDependency`
- `CharacterDefinition`、`CardDefinition`、`RelicDefinition`
- `PowerDefinition`，覆盖自定义 Buff、触发器和生命周期回调的能力描述
- `EnemyDefinition`、`EncounterDefinition`、`EventDefinition`
- `RewardDefinition` 和资源变更
- `HookCapability`，描述 Mod 需要的生命周期、战斗、房间、地图和 UI 接缝
- `CompatibilityReport`，记录已发现能力、已接入能力、未支持能力、错误分类和证据摘要

外部类型只存在于 adapter 和 worker 边界。缺少语义时返回 `Unsupported` 并保留证据，不把空实现当作兼容。

### 日志和 manifest

适配运行沿用现有 `build-manifest` 和 `run-manifest` 的身份链，并增加以下字段。

- 快照摘要、Workshop ID、Mod ID 和 Mod 版本
- 选中的游戏兼容变体和依赖解析结果
- 输入文件摘要、适配器版本、配置摘要和随机种子
- 发现能力、转换数量、未支持能力和失败分母
- worker 进程身份、写入拦截结果、重放摘要和确定性摘要

完整 Mod 目录只在固定快照中保留。单次运行目录只保留最小元数据、日志、trace 和必要的哈希引用。

## 分阶段执行方案

### 阶段 0：快照和来源固定

状态为已完成。

交付是固定 Workshop 快照、逐文件 SHA-256 清单和来源边界。验收条件是源与副本的路径、大小和摘要完全一致，后续更新只能创建新快照。

### 阶段 1：发现、版本和依赖解析

先不执行角色玩法。

交付内容包括 manifest 解析器、稳定排序、版本约束解析、依赖图、兼容变体选择和 `CompatibilityReport` 初版。覆盖全部 21 个条目，尤其验证 RitsuLib 与 YukiMakoto 的 `0.111.0` 变体。

验收条件如下。

- 每个条目能被发现并绑定到 Workshop ID 和快照摘要。
- 缺 manifest、重复 ID、非法版本、缺依赖和无精确兼容变体都有稳定错误码。
- 解析结果两次运行完全一致。
- 解析器不会触碰真实 Workshop 目录以外的路径，也不会写入快照。

### 阶段 2：最小标准模型和测试夹具

先用仓库内合成 fixture 证明适配边界，再接入真实 DLL。

最小模型覆盖一个角色、一张卡、一个遗物、一个 Power、一个敌人、一个事件、一个奖励和一个资源结果。建立正常、缺字段、非法值、重复 ID、缺依赖、不支持版本、无效格式和确定性失败夹具。

验收条件是转换结果稳定、错误分类稳定、输入哈希稳定，失败不会污染正式注册表，也不会生成无界构建产物。

### 阶段 3：第一个简单角色纵向切片

首选 Watcher，备选 Aemeath。只选择一个，不并行接入全部角色。

切片必须走完角色选择、初始卡组和遗物、首场战斗、卡牌或遗物奖励、离开战斗、结束清理和同构建重放。自定义内容只在探针实际发现后纳入能力清单。

验收门如下。

- 新进程中完成至少一场真实原生战斗。
- 角色、卡牌、遗物、Power 和奖励身份均能回到内部标准模型。
- 相同快照、游戏版本、种子和动作脚本产生相同摘要。
- 任何未实现的生命周期或 UI 依赖都被准确归类为 `Unsupported`，不会静默跳过。

### 阶段 4：卡牌、遗物和自定义 Buff 扩展

先扩展与战斗状态直接相关的内容表面。建立触发时机、目标选择、资源变更、持续回合、死亡和战斗结束清理的最小契约。

优先验证 Remilia、LexNinja2 或 YukiMakoto 中一个 RitsuLib 依赖角色。RitsuLib 使用精确的 `0.111.0` 变体，禁止调用其他兼容目录作为替代。

验收是能逐项列出已支持和未支持的卡牌、遗物、Power 与 Hook，不以“Mod 加载成功”代替玩法兼容。

### 阶段 5：自定义敌人、遭遇、事件和奖励

建立敌人意图、敌人行为、事件选项、房间转移、奖励生成和资源账本的适配边界。每个新增表面先用单行为 fixture，再组合进角色纵向切片。

优先从 Kaguya、St2bs 或 Downfall 中选一个小范围内容。完整第四幕、多 Boss、多角色和大型地图不作为本阶段的首个验收目标。

验收是一个最小自定义敌人或事件能进入真实生命周期并完成 teardown，未覆盖的地图、UI 或保存语义必须停在清晰的兼容报告中。

### 阶段 6：MinionLib 和复合依赖

在基础 Power、敌人和资源契约稳定后接入 MinionLib，再尝试 Shadowverse Beyond Mod。先验证 Minion 注册、随从生命周期、组件卡牌和跨 Mod 依赖，不直接追求整包通关。

验收是依赖解析、加载顺序、随从生命周期和失败隔离均可重放，且不会把 MinionLib 特有语义硬编码进核心模型。

### 阶段 7：批量兼容矩阵和回归

将全部快照条目放入静态发现矩阵和运行时能力矩阵。资源类、QoL 类和非玩法 Mod 作为加载和隔离样本，角色类按能力表逐步扩展。

最终报告必须同时给出成功分母、失败分母、未运行条目、失败错误码、游戏版本、快照摘要和已知限制。性能优化、策略优化和大规模全内容接入等工作在此阶段之后另行规划。

## 建议的执行顺序和阻塞关系

以下是下一轮 `/to-tickets` 应生成的垂直切片。当前只记录计划，不向 GitHub 发布问题。

1. 固定快照来源与校验入口。已完成。
2. ModCatalog 与版本依赖解析。阻塞于 1。
3. 只读 worker 与 ModManager 文件视图。阻塞于 2。
4. 内部标准模型、错误码和合成 fixture。阻塞于 2，可与 3 并行设计。
5. Watcher 首战纵向切片。阻塞于 3、4。
6. RitsuLib `0.111.0` 变体和一个角色适配。阻塞于 5。
7. 自定义 Power、卡牌和遗物语义。阻塞于 5。
8. 一个自定义敌人或事件的最小闭环。阻塞于 7。
9. MinionLib 和 Shadowverse 最小复合闭环。阻塞于 7、8。
10. 全量兼容矩阵、回归和验收报告。阻塞于 5 至 9 的实际结果。

每个切片都应在新进程、新运行目录和固定快照下独立验收。阶段通过后再进入下一阶段，遇到未支持语义就停在兼容报告，不以补丁或空实现掩盖缺口。

## ask-matt 路由结论

这项工作属于多会话、存在未知运行时决策的大型工作。建议先用 `grill-with-docs` 把术语和不可逆边界写入仓库，再用 `wayfinder` 处理仍未明确的决策，完成后转为 `to-spec` 和 `to-tickets`，最后按阻塞关系逐个实现。当前已完成来源固定和初步静态盘点，尚未创建 GitHub 问题，也没有修改现有源码。
