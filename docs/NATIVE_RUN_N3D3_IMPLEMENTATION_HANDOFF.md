# 4D3 精英、Boss 与步骤5准备

本交接承接 4D2 原生事件/事件战斗；实施入口需以最终独立审查通过的 4D2 冻结为准。M1 全六步仍已授权，内部验收后直接继续，不逐步向用户请批。当前不做公开 Mod SDK 或 Eleanor 新适配。

4D2 独立审查曾发现新 profile 替换旧 room contract 后遗漏清理/到达约束，以及父任务与奖励子任务的完成顺序未绑定。修复详见 `NATIVE_RUN_N3D2_REVIEW_REPAIRS.md`，以该轮 closeout 及后续独审为入口。4D3 必须明确列出它实际消费的全部原生记录和继承的契约；旧 profile 的负控通过不能代替新 profile 的同类控制。对静止边界使用不可变完整锚点，对真正战斗/奖励业务区间保留合法状态变化。不要用 IsFinished 或累计胜利数替代当前任务/战斗实例的真实完成。

最新修复见[4D2完整状态绑定](NATIVE_RUN_N3D2_STATE_BINDING_REPAIRS.md)，仍需独立复审。新控制器须把父操作/真实任务输入接到子集合入口，按原生方法定义完整转换；仅绑定子返回/确认仍允许整子树共同篡改。未完成任务的外层返回也须绑定已验证阶段，不能跳过完整状态或强制任务先完成。

## 已经可以复用的基础

- 固定 v0.111.0 /41cef1ea、Ironclad/A0、正常 Neow 开局、独立内存档案及同构建源锁。
- 原生 Battle/CardPlay/EndTurn，清理前胜利与历史记录、真实死亡及 terminal stamp、原生奖励会话和具体取得实例、合法地图行进与新战斗 DeckVersion 关联。
- 原事件进入子 CombatRoom 后，使用实际 ProceedFromTerminalRewardsScreen → 原生子房间 Exit → 同一 EventRoom.Resume → 真实 BattlewornDummy.Resume Task；外层返回、实际完成、错误及预算停止分别记录。恢复后通过原生地图行进到新战斗首个 Play。
- 4A 只提供 ActReady/原生幕转换与 Architect 尾部 API 夹具；没有正常开局自然完整通关。不能将该夹具当作本轮 Boss 胜利或步骤5自然跨幕证据。

## 第一工作包：原生精英与第一幕 Boss 的有限夹具

先从固定 DLL 核验本次默认 Act、原生可抽取 Encounter 列表、RoomType 和实际模型身份，预登记一个精英与一个第一幕 Boss；不要凭名称猜 encounter 或在失败后更换样本。可以用已审查 RunManager.EnterRoomDebug 的原生房间/模型入口建立清晰 API 夹具，记录此前真实正常流程产生的 HP/牌组/遗物/药水。

沿用4D2的做法：合法选择与原生命令建立可执行前缀；弱策略死亡、预算停止及未知选择保留。需要更强策略时版本化实际决策规则和预算，奖励/升级/商店等资源必须从真实业务取得。不能为获胜直接修改 HP、能量、敌人或牌组，不把搜索预测当真实执行。

重点复核 CombatRoom.StartCombat、BeforeCombat/AfterSetup、Boss 特殊阶段和纯展示边界。`.build/review/n3-handoff/Rooms.CombatRoom.cs` 只是已有本机定位资料，必须核对固定 DLL 实际方法后再适配。TestMode 下 UI 不在场会省略自动奖励路径，需复用原生业务入口并保证唯一生成/领取，不用 UI 缺失当作无奖励的依据。

## 第二工作包：奖励与 act-ready

| 边界 | 必须记录/验证 |
| --- | --- |
| 开始/战斗 | 真正 encounter/room/creature 实例、阶段、玩家合法决策、敌方动作、完整 RNG、原始伤害/格挡与清理前历史 |
| Victory/Death | 原生终态调用和触发动作；死亡不领奖；不能将普通精英/Boss结束当 RunVictory |
| 奖励 | 原生 ShouldGiveRewards、Generate/Offer/Hook实际调用链、集合是否存在、所选/拒收/替换/跳过及实际取得。最后 Boss 合法无普通奖励单列 |
| 幕末准备 | 仅在真实 Boss 完成及必需奖励收尾后允许对应生产 ready/投票入口。4A 的提前构造尾部条件不能移作自然流程 |
| 后续 | 准备记录 ActChangeSynchronizer、实际 EnterNextAct Task、旧投票拒绝/忽略、持久状态及新幕首决策；自然跨幕在步骤5正式收口 |

先列完整生命周期，不把所有相邻快照都当静止。请求/结果/任务必需唯一、父子归属与顺序、静止完整状态、真实业务变化、新旧实例、完整 RNG、错误和未确认前缀都需随实现进入生产 reader。负控应包含共同篡改、未知嵌套字段及合法等价；不能仅检查几个计数或外层 exit0。

## 第三工作包：自然节点与步骤5

在版本化自然控制器中连接既有战斗、奖励、Rest/升级、事件、商店、宝箱和本轮精英/Boss。至少实际从合法地图进入新类别、完成原生业务并继续下一决策；API 夹具与自然样本分别列。

4D2 的策略仅覆盖 Hollow Gold 选项和 Dummy Setting1，Hug 变牌及 Setting2/3 尚未验证，候选里明确不支持。4D2 的 Dummy 胜利使用真实沿途攻击卡和实际奖励药水，前期初始牌组超时保留为策略失败，不是原生机制缺陷。不要将这些有限路径扩写为所有事件、所有卡或可靠胜率。

步骤5需形成同一正常开局 Run 经默认 Acts 到真实 Architect/RunVictory 的自然连续证据，以及真实死亡。保留地图/内容范围、策略、信息模式、预算和失败分母。商店特殊拾取、多取卡、卡/遗物补货、更多 Hook、多会话及长期临时状态按实际可达内容门完成，未知行为明确停止。4D2的 map/from/to 与运行时合法检查不等于已导出整幕地图和所有合法边；完整 run 的候选/地图与跨节点数据契约仍需在步骤5整合。

步骤6再冻结批测和可分析数据，区分流程可靠性、机制覆盖、策略表现与性能。不要用同种子重复当独立样本。记录真正的必要内容及观察成本，再优化；不关闭校验换速度。

## 集成门与安全

沿用15锁定Mod输入/52兼容源码冻结及当前原版回归；新增控制器只发展内部边界。每次最终源/产物冻结后，同一构建执行适用回归和负控，历史失败保留，不用旧构建的成功替代最终构建结果。

保持一个 Run 一个进程、MemorySaveStore、保存/replay/Telemetry隔离和未知 Harmony patch 拒绝；新增方法补实际未知补丁审计，审计 API 夹具与游戏业务分别说明。未知额外宿主权限、真实 Steam/网络/存档依赖或必须放宽审计时停止相应动作并给明确方案，其余独立工作继续。仅 Lab 内写入，不改角色、安装或用户存档，不启动游戏 UI，不提交推送，不重置已有 dirty 工作。

下一轮应先检查多战斗等待边界：现有 WaitBoundary 的累计 BattleVictories>0 只是旧单片段信号，不能把新战斗尚未启动的间隔当作上次胜利。当前固定事件样本在原生 EnterMapCoord 后实际到达 Play；扩展一般循环时应按具体 combat/房间实例及开始结束序列等待和归属，不凭累计数判断当前战斗。
