## 下一最小工作包

1. **先做内部能力组合。** 当前原生奖励、事件、商店等Active标记按专用scenario分开，不能仅用一个while连接就覆盖全run，也不能临时改`NativeLifecycle.Scenario`伪装旧场景。建立有限、启动时锁定的内部能力配置和房间契约组合，复用现有真实原生命令与选择接口。新Harmony观察方法在启动时登记并做实际未知补丁拒绝测试，保持全程patch稳定；不在到达节点时偷偷加补丁。
2. **连接已完成的节点能力。** 优先接入现有商店、Hollow Gold、休息/升级、宝箱、药水以及正常奖励选择；先让三个开发样本都能合法继续到各自真实终局或新具体unsupported。原失败样本不替换，旧预算/策略结果保留，新策略版本单列。
3. **改善合法可达性。** 当前夹具只经过一场普通战斗，11张牌的薄准备不足以证明Boss战后路径。下一版应从真实沿途奖励、升级、遗物、药水和合法策略获得准备，而不改HP、能量、敌人或永久牌组。卡奖励决策可以按公开候选改进并版本化；不能悄悄改变旧索引或将不同策略合并为重复结果。可以使用明确Oracle策略；不要把有限预算结论称全局最优。
4. **先闭合一个实际精英及第一幕Boss的胜利和奖励。** 固定原有夹具Encounter不换失败对象；自然路径使用原生生成的实际Boss。逐动作记录原生结果，Victory后完成唯一原生奖励及必要子选择，真实取得实例/拒收/替换与父子返回一并校验。没有成功取得的奖励不填成功；没有Victory就不进入ready。
5. **原生ready及下一幕。** 在本次真实Boss和奖励完成后调用原生ready同步器，等待实际EnterNextAct任务；记录旧票据/投票处理、HP/Gold/deck/relic/potion持久状态、临时战斗状态、mapGeneration及新幕首决策。API夹具跨幕与正常开局自然跨幕分列。

## 进入步骤5–6前的依赖

`LastVictoriousRoom`消除了“旧累计胜利数代表新房间胜利”的具体问题，但不能据此宣称同一房间内所有重新开战/多阶段Boss已覆盖。一般控制器还需核对实际combat实例、开始/结束序列与当前阶段，针对固定Boss的真实行为设门。

当前地图记录来自实际Children并在执行时核验原生守卫；完整公开地图及合法边的独立数据契约仍应在通用控制器收口。永久牌组当前基础投影以实例/model/upgrade为主，遇到附魔/额外永久变化需加入真实原生序列化内容并声明来源，不能用数量相等覆盖内容差异。

当前奖励生成门校验非Rewards-RNG完整状态及该流counter/状态字的一致步进，没有独立重算整个候选池/抽取次数。原生调用、固定重放和小型独立数值契约分别说明，避免将局部数据门称完整规则镜像。新遗物/Hook副作用按真实触达验证，不对当前有限帧外变化强行通过。

新的原生片段保留规范JSONL追加记录；`events.json`便捷导出仅在结束时写一次，并将导出异常明确记DataError。测量记录证明此前该重复导出是主要开销；不同并发负载下不声称通用加速倍数。长run仍要测量身份缓存、状态复制、日志容量与内存，再决定分块/流式索引，不能关闭校验换速度。

旧header的`stateScope`含共享4C投影说明，精确范围以注册scenario、当前契约和实际字段为准；进入通用run时统一版本化配置/数据scope，避免自由说明字段承担权威判断。观察最小/off仍保留必需投影，不声称零观察器。

步骤5要求同一正常开局Run经默认Acts至真正Architect/RunVictory和新进程重放；尾部夹具或早死不能代替。步骤6按已预登记EVAL01–06运行/重放并交付可分析数据，保留死亡、不支持、预算、执行错误和数据错误分母。
