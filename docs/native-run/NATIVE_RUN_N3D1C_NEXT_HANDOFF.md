# 4D1C 后续交接：奖励语义闭环、事件与 Boss

本轮实现完成后须先独立验收 [4D1C 生命周期契约](NATIVE_RUN_N3D1C_LIFECYCLE_CONTRACT.md) 与最终证据。用户持续完成 M1 的授权有效，接续工作不等待逐步请批。总范围仍以 [4D 主交接](NATIVE_RUN_N3D_IMPLEMENTATION_HANDOFF.md) 和 [M1 方案](../milestones/MILESTONE_1_NATIVE_RUN_PLAN.md) 为准。

## 当前可复用基础

原生正常库存与地图商店进出、卡/药水/移除交易已有严格旧 profile。新增交易 profile 覆盖无特殊拾取效果的遗物原生购买、真实默认 AfterObtained、MawBank 的真实购买 Hook，以及 Courier 两次原生药水补货。请求含 entry/当前商品实例/价格，旧票据拒绝，实际新旧实例、完整静止状态、价格及 RNG 分阶段关联。不得通过放宽旧完整快照断言来加入新效果。

当前限定：特殊拾取选择/效果、卡牌与遗物补货、额外购买监听器、替换/拒收等组合尚未覆盖。实际原生动作可发生变化，未来扩展必须以具体业务调用和独立结果契约验证；现有窄 profile 的通过不自动准许这些组合。自然购入切片 DEV_02/03 的可达性停止应保留，通用 run 策略需支持合法无购买离店。

当前商店状态与校验器仍按单商店切片组织。步骤 5 的多商店 run 应按实际 session 创建控制器、库存版本和价格账本，并验证跨店资源延续；不能重置全局计数器来冒充连续运行。

## 下一有界轮次：原版奖励与取得结果

1. 复用 `NativeRewards.CardChoice` 的选择源，检查并接入原生 Driftwood reroll 的同一 OnSelect 多菜单循环。当前 `pendingCards.ContainsKey(reward)` 会在第一菜单未闭合时拒绝第二菜单；须重构为同 reward 的有序菜单实例链，保存每次请求、决策、菜单结果及最终原生取得。按实际原生语义区分“重选菜单完成”和“领取完成”，禁止默认取第一项或手动重新生成奖励。
2. `CardAfter` 当前以 `pending.Card` 仍在牌组作为取得条件。改为原生 CardPileAddResult 的 selected/actual/declined/modifyingModels 契约，核实 FresnelLens 在候选生成还是实际取得阶段发生作用，再设计最小夹具。所选旧实例与实际新实例分别记录，永久牌组完整内容、升级、引用及真实历史须一致。
3. `Collect` 当前药水成功且原物不在库存即抛 Unsupported；须支持原生 Sozu NotAllowed 与满槽 TooFull 的不同结果。奖励完成、效果取得、成功付款或拒收分开记录，不能把处理完奖励当成拿到药水。保留容量、槽位与实际对象对应。
4. 将使用已知 seed 的 Neow 内部 CardReward 迁入同一新奖励会话协议，保留旧 GoldenPearl 24 动作回归。之后补 SpoilsMap 原生修改奖励的来源账本，不以未修改夹具代替 Hook 路径。

实现前先核实原生具体方法与返回值，再写完整父子契约：必需/唯一、归属、顺序、菜单/对象版本、静止完整状态、真实业务变化及清理前数据。正负控覆盖整体遗漏、重复、错序、旧请求借用、共同篡改、完整内容及合法等价。API 夹具和自然片段分列，固定样本不替换。

每轮固定 dirty 源码、构建和输入；同最终构建复跑适用 1–4D 原生矩阵、历史生产控制、自然/重放/RNG及失败前缀。15 个输入与 52 个兼容源码继续冻结。仅 Lab 和隔离实验，不改角色/安装/真实存档、不启动 UI、不调用真实 Steam/网络、不提交推送。架构保持原生执行与数据优先，不增加公开 Mod SDK，也不把 finite budget 或固定策略样本解释成整局胜率。
